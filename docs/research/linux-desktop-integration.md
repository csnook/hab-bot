# How a Tauri 2 app fits into Linux desktops through freedesktop.org conventions

Research for [csnook/hab-bot#3](https://github.com/csnook/hab-bot/issues/3). It covers how a Tauri 2 app on Linux starts at login in the tray, shows alerts with action buttons and sounds, opens a single-instance window from the tray, finds location and nearby Wi-Fi, Bluetooth and USB devices, and what changes under Flatpak and Wayland.

- **Read on:** 2026-09-27. The version or branch of each source is in [Access notes](#access-notes).
- **Terminology:** following `CONTEXT.md`, a desktop notification is one kind of **alert**. "Notification" below means only the operating-system mechanism. Complete and Snooze act on an **occurrence**. A watched Wi-Fi network, Bluetooth device or USB device would be a **source** of a Wi-Fi, Bluetooth or USB **source class**, supplying **triggers** (for example, arriving) or **conditions** (for example, being at home).
- **What was not verified:** the proxy blocked every freedesktop.org, Tauri-website, docs.rs, KDE and GNOME documentation host (full list in [Access notes](#access-notes)). None of the specifications themselves (Desktop Notifications, Autostart, Desktop Entry, Sound Theme, Sound Naming, StatusNotifierItem) could be read. Claims about them come from the D-Bus interface files and server code that implement them. Claims that rest only on a search-engine excerpt are marked **[unverified: search excerpt]**. Conclusions drawn from reading code, but not tested, are marked **[inferred from source]**. Nothing was run on a real desktop.

## Summary

- **Autostart.** `tauri-plugin-autostart` 2.6.0 depends on `auto-launch` 0.5.0. That crate writes a minimal XDG autostart file to `~/.config/autostart/<name>.desktop`, and it hard-codes the path rather than reading `$XDG_CONFIG_HOME`. A sandboxed app, or a host app with an app ID, can instead call the Background portal's `RequestBackground` with `autostart: true`. The portal then writes `<app-id>.desktop` itself.
- **Tray.** Tauri 2.12's tray goes through `tray-icon` 0.25 with its libappindicator backend. This speaks KDE's StatusNotifierItem (SNI) D-Bus protocol, so Plasma shows it natively. GNOME needs the AppIndicator extension. **On Linux, Tauri emits no tray click events.** The only thing a click can do is open the tray menu. `tray-icon` has a pure-Rust `ksni` backend that does report left and middle clicks, but Tauri 2.12 does not turn it on.
- **Staying alive with no window.** When the last window is destroyed, Tauri emits `RunEvent::ExitRequested { code: None }`. Calling `prevent_exit()` keeps the process and its tray running.
- **Alerts with actions.** On desktop, Tauri's notification plugin uses only the title, body, icon and sound. Action buttons are mobile-only. Complete and Snooze buttons therefore need custom D-Bus code: `org.freedesktop.Notifications` through `notify-rust` or `zbus`, or the Notification portal through `ashpd`. Plasma 6.7 and GNOME Shell both support actions, persistence and sound hints. Plain D-Bus action signals reach only a process that is still running. Portal notifications are meant to outlive the app and restart it through D-Bus activation. Plasma's portal backend implements only version 1, which has no sound field.
- **Sounds.** Plasma plays the `sound-name` or `sound-file` hint through libcanberra, using the user's sound theme. GNOME plays these hints too. No maintained Rust crate for sound-theme playback was found. The `freedesktop-sound` crate only looks up files.
- **Single instance.** `tauri-plugin-single-instance` 2.5.0 owns the session-bus name `<identifier>.SingleInstance` and forwards `argv` and `cwd` to the running instance. Tauri's documentation page still gives the older name, `org.<id>.SingleInstance`.
- **Location.** Tauri's geolocation plugin does not support Linux. The options are the Location portal, which is backed by GeoClue and adds a per-app permission dialog, or GeoClue directly on the system bus. The `robius-location` crate does the first with a fallback to the second, and it also covers Android.
- **Wi-Fi, Bluetooth and USB.** No portal exposes the name (SSID) of the Wi-Fi network: the NetworkMonitor portal gives only availability, metering and connectivity. The current network comes from NetworkManager's D-Bus API. Bluetooth connections come from BlueZ's `org.bluez.Device1.Connected`. USB hotplug comes from udev netlink events, which the pure-Rust `nusb` crate can read. All three need extra Flatpak permissions.
- **Flatpak.** The Flatpak build needs:
  - `--talk-name=org.kde.StatusNotifierWatcher` for the tray, plus a bundled libayatana-appindicator and a writable directory for the icon file.
  - The Background portal for autostart. The portal also watches apps that run without windows.
  - `--system-talk-name` for NetworkManager and BlueZ.
  - `--device=usb` or the USB portal for USB devices.
- **Wayland.** Bringing a window to the front needs an xdg-activation token. Plasma supplies one to tray items (through `ProvideXdgActivationToken`) and to notification clients (through the `ActivationToken` signal). None of `tray-icon`, `ksni`, `tao`, `notify-rust` or the single-instance plugin uses these tokens. Without one, KWin grants a token only to an app with focus or recent input, so the window may only be flagged for attention instead of raised **[inferred from source]**. Window positioning and always-on-top do not work on Wayland.

## 1. Starting at login in the tray, and running with the window closed

### 1.1 XDG autostart

- **Tauri's plugin.** `tauri-plugin-autostart` 2.6.0 declares Linux support as "full". It exposes `enable`, `disable` and `isEnabled` to Rust and JavaScript ([autostart.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/autostart.mdx); [Cargo.toml](https://docs.rs/crate/tauri-plugin-autostart/2.6.0/source/Cargo.toml)). The builder takes launch arguments such as `.arg("--from-autostart")` and an `app_name` override. The name defaults to `app.package_info().name` ([src/lib.rs](https://docs.rs/crate/tauri-plugin-autostart/2.6.0/source/src/lib.rs)). On Linux the command registered is the AppImage path when the app runs as an AppImage, and the current executable otherwise (`src/lib.rs` L251–259).
- **What gets written.** The plugin depends on `auto-launch = "0.5"` (0.5.0 in its `Cargo.lock`). In `auto-launch` 0.5.0, `enable()` writes `~/.config/autostart/{app_name}.desktop`. The file contains `Type=Application`, `Version=1.0`, `Name`, `Comment`, `Exec={path} {args}`, `StartupNotify=false` and `Terminal=false`. `disable()` deletes the file, and `is_enabled()` checks that it exists ([src/linux.rs](https://docs.rs/crate/auto-launch/0.5.0/source/src/linux.rs) L32–84). From the code:
  - The directory is built from `dirs::home_dir()` plus `.config/autostart`, so `$XDG_CONFIG_HOME` is ignored.
  - The `Exec` value is written without quoting or escaping.
  - The file name comes from the app's name, not a reverse-DNS app ID.
- **Newer `auto-launch`.** Version 0.6.0 adds a `LinuxLaunchMode` with `XdgAutostart` and `Systemd` (a systemd user service enabled with `systemctl --user enable`) ([src/linux.rs](https://docs.rs/crate/auto-launch/0.6.0/source/src/linux.rs)). The Tauri plugin has not moved to it.
- **How autostart files are consumed.** systemd's `xdg-autostart-generator` scans the user's config directory and the system config directories for `/autostart`. It turns each entry into an `app-<name>@autostart.service` pulled in by `xdg-desktop-autostart.target` ([xdg-autostart-generator.c](https://github.com/systemd/systemd/blob/main/src/xdg-autostart-generator/xdg-autostart-generator.c) L52–76; [xdg-autostart-service.c](https://github.com/systemd/systemd/blob/main/src/xdg-autostart-generator/xdg-autostart-service.c) L63, L700–702). It reads these keys (L323–336):
  - `Name`, `Exec`, `Path`, `TryExec` and `Type`
  - `OnlyShowIn`, `NotShowIn` and `Hidden`
  - `AutostartCondition`, `X-KDE-autostart-condition`, `X-GNOME-Autostart-Phase` and `X-systemd-skip`

  It skips any entry that is not `Type=Application`, has no `Exec`, or has a `TryExec` binary that is missing (L540–580). Whether Plasma 6.7 starts autostart entries through this generator by default was not verified. The Autostart specification itself could not be read.
- **The portal route.** `org.freedesktop.portal.Background` (version 2) offers `RequestBackground`. Its options are `reason`, `autostart`, `commandline` and `dbus-activatable`. It replies with the booleans `background` and `autostart`. A second method, `SetStatus(message)`, sets a one-line status of fewer than 96 characters ([org.freedesktop.portal.Background.xml @1.22.0](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/data/org.freedesktop.portal.Background.xml)). xdg-desktop-portal 1.22.0 implements autostart by writing `g_get_user_config_dir()/autostart/<app-id>.desktop`. That file has `X-XDP-Autostart=<app-id>`, `Exec` taken from `commandline`, and `DBusActivatable=true` if requested. The call fails with "Autostart not supported (no AppId detected)" when no app ID is known ([src/background.c](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/src/background.c) L797–880). Host (unsandboxed) apps get the background permission without a dialog (L918–921).
- **Host apps need an app ID for portals.** xdg-desktop-portal takes a host app's ID from its systemd unit name, `app[-<launcher>]-<ApplicationID>-<RANDOM>.scope` ([src/xdp-app-info-host.c](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/src/xdp-app-info-host.c) L115–190). An app can also call `org.freedesktop.host.portal.Registry.Register(app_id)`. That call must come before any other portal call, and the ID "must be able to match the basename of a .desktop file" ([org.freedesktop.host.portal.Registry.xml](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/data/org.freedesktop.host.portal.Registry.xml)).
- **Rust bindings.** `ashpd` 0.13.13 (built on zbus) has modules for `background`, `notification`, `location`, `network_monitor`, `usb`, `registry` and `activation_token`, plus `is_sandboxed()` ([src/](https://docs.rs/crate/ashpd/0.13.13/source/src/)).

### 1.2 Tray icon (StatusNotifierItem)

- **Tauri API.** The tray needs the `tray-icon` Cargo feature. It is used through `TrayIconBuilder` in Rust or `TrayIcon.new` in JavaScript ([system-tray.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/learn/system-tray.mdx)).
- **Backend.** `tauri` 2.12.0 depends on `tray-icon` 0.25 with the features `serde` and `libappindicator` ([Cargo.toml](https://docs.rs/crate/tauri/2.12.0/source/Cargo.toml)). `tray-icon` has two Linux backends: `libappindicator` (the default, which needs GTK 3, libxdo, and libappindicator or libayatana-appindicator) and `ksni` (SNI over D-Bus, with no system libraries unless a muda GTK backend is also on). If both are on, `ksni` wins and Cargo prints a warning ([README.md](https://docs.rs/crate/tray-icon/0.25.1/source/README.md) L7–35; [src/lib.rs](https://docs.rs/crate/tray-icon/0.25.1/source/src/lib.rs) L17–20).
- **Loading the library.** `libappindicator-sys` 0.9.0 loads `libayatana-appindicator3.so.1` at run time, then tries `libappindicator3.so.1` ([src/lib.rs](https://docs.rs/crate/libappindicator-sys/0.9.0/source/src/lib.rs) L14–36). Tauri's `.deb` adds a dependency on `libappindicator3-1` when the tray is used ([debian.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/distribute/debian.mdx) L11).
- **AppIndicator is SNI.** libayatana-appindicator exports the `org.kde.StatusNotifierItem` interface ([src/notification-item.xml](https://github.com/AyatanaIndicators/libayatana-appindicator/blob/main/src/notification-item.xml)).
- **No click events.** Tauri's documentation says: "Linux: Unsupported. The event is not emitted even though the icon is shown and will still show a context menu on right click" ([system-tray.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/learn/system-tray.mdx) L233–235; [src/tray/mod.rs](https://docs.rs/crate/tauri/2.12.0/source/src/tray/mod.rs) L62–67). The same file lists other Linux limits:
  - The icon is sometimes invisible unless a menu is set.
  - A menu, once set, cannot be removed.
  - Tooltips are unsupported.
  - The title shows only next to an icon.
  - The icon is written to a temporary directory (L214–290).
- **Why there are no clicks.** Until 0.6.0, libayatana-appindicator did not handle `Activate`. Version 0.6.0 (2026-06-10) added an `activate-event` signal. When nothing is connected to it, `Activate` still returns `UnknownMethod` "so the panel falls back to showing the context menu" ([src/app-indicator.c](https://github.com/AyatanaIndicators/libayatana-appindicator/blob/main/src/app-indicator.c) L1352–1366; [ChangeLog](https://github.com/AyatanaIndicators/libayatana-appindicator/blob/main/ChangeLog)). The Rust `libappindicator` 0.9.0 bindings (2023) and `tray-icon`'s GTK backend do not connect to it (no `activate` handling in [src/platform_impl/gtk/mod.rs](https://docs.rs/crate/tray-icon/0.25.1/source/src/platform_impl/gtk/mod.rs)).
- **The `ksni` backend.** It emits `Click { button: Left }` on `Activate` and `Click { button: Middle }` on `SecondaryActivate`. "The StatusNotifier host handles right clicks itself", and `rect` is empty ([src/lib.rs](https://docs.rs/crate/tray-icon/0.25.1/source/src/lib.rs) L601–608; [src/platform_impl/ksni/mod.rs](https://docs.rs/crate/tray-icon/0.25.1/source/src/platform_impl/ksni/mod.rs) L150–172). Tauri 2.12 exposes no feature to select it. Adding `tray-icon` directly with `features = ["ksni"]` would, through Cargo feature unification, switch Tauri's tray to KSNI. **This is not documented by Tauri and was not tested.**
- **Plasma's tray.**
  - A left click opens the context menu if the item has `ItemIsMenu` set, and otherwise calls `Activate(x, y)`. A right click opens the context menu, and a middle click calls `SecondaryActivate` ([StatusNotifierItem.qml @Plasma/6.7](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/applets/systemtray/qml/StatusNotifierItem.qml) L44–78).
  - Before `Activate`, `SecondaryActivate` or `ContextMenu`, Plasma obtains an xdg-activation token and calls `ProvideXdgActivationToken(token)` on the item ([systemtray.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/applets/systemtray/systemtray.cpp) L570–651). This method is a KDE addition to `org.kde.StatusNotifierItem` ([org.kde.StatusNotifierItem.xml](https://github.com/KDE/kstatusnotifieritem/blob/master/src/org.kde.StatusNotifierItem.xml) L52).
  - Plasma's tray also lists "background apps" reported by the portal's background monitor (`org.freedesktop.background.Monitor`, property `BackgroundApps`). For each one it offers "open", which relaunches the app's `.desktop` entry with an activation token, and "stop", which calls `org.freedesktop.Application.quit` or falls back to `flatpak kill` ([systemtraymodel.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/applets/systemtray/systemtraymodel.cpp) L475–583).
- **GNOME.** The "AppIndicator and KStatusNotifierItem Support" extension (GNOME Shell 45–51) adds SNI items to GNOME Shell. It reveals menus on click and activates the app window on double-click "if implemented by the indicator" ([README.md](https://github.com/ubuntu/gnome-shell-extension-appindicator/blob/master/README.md); [metadata.json](https://github.com/ubuntu/gnome-shell-extension-appindicator/blob/master/metadata.json)). Whether stock GNOME Shell shows SNI items without the extension was not checked in GNOME's own source. Flatpak's documentation warns that "a number of Linux distributions don't show status icons", and recommends status icons only "in a supplementary manner … These include 'minimize to tray'" ([desktop-integration.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/desktop-integration.rst) L62–71).
- **The SNI specification** is a freedesktop.org wiki page, which was blocked. According to `ksni`'s documentation, the specification recommends falling back to the XEmbed System Tray specification when no host exists ([src/lib.rs](https://docs.rs/crate/ksni/0.3.6/source/src/lib.rs) L271–286). XEmbed icons need X11 ([desktop-integration.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/desktop-integration.rst) L73–74).
- **Races at login.** `ksni` returns `Error::WontShow` when no StatusNotifierHost exists: "Starting the tray before the initialization of the desktop environment finished may cause this error." It offers `assume_sni_available(true)` to wait for the watcher instead ([src/lib.rs](https://docs.rs/crate/ksni/0.3.6/source/src/lib.rs) L271–290, L380–397). `tray-icon`'s KSNI backend calls a plain `spawn()` ([ksni/mod.rs](https://docs.rs/crate/tray-icon/0.25.1/source/src/platform_impl/ksni/mod.rs) L30–43), so it would fail if started too early **[inferred from source]**. How the libappindicator backend behaves at login was not checked.

### 1.3 Running with the window closed

- When the last window is destroyed, `tauri-runtime-wry` calls `RunEvent::ExitRequested { code: None }`. If the handler calls `api.prevent_exit()`, the event loop keeps running ([src/lib.rs](https://docs.rs/crate/tauri-runtime-wry/2.12.0/source/src/lib.rs) L4272–4287; [tauri src/app.rs](https://docs.rs/crate/tauri/2.12.0/source/src/app.rs) L79–95, L225–232). `code` is `None` for user-initiated exits and `Some` for `AppHandle::exit` or `restart`. `restart` ignores `prevent_exit`.
- The alternative is to call `CloseRequestApi::prevent_close()` on `WindowEvent::CloseRequested` and hide the window instead (`src/app.rs` L97–105). Tauri's tray example shows the window with `unminimize()`, `show()` and `set_focus()` ([system-tray.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/learn/system-tray.mdx) L280–300).
- Under Flatpak, a process with no windows is watched by the portal's background monitor ([§5](#5-what-changes-under-flatpak)).

## 2. Alerts with action buttons, and sounds

### 2.1 The Desktop Notifications D-Bus protocol (`org.freedesktop.Notifications`)

The specification was blocked. As implemented by Plasma and GNOME, `Notify` takes an action list of `id, label` pairs and a hints dictionary. The server emits three signals: `ActionInvoked(u id, s action_key)`, where `default` means the body was clicked; `NotificationClosed(u id, u reason)`; and `ActivationToken(u id, s token)`. Both servers report specification version "1.2". The `ActivationToken` signal "can be emitted before an ActionInvoked signal … Clients should not assume the server will generate this signal" **[unverified: search excerpt of https://specifications.freedesktop.org/notification/1.2/protocol.html]**.

**Plasma 6.7** ([libnotificationmanager](https://github.com/KDE/plasma-workspace/tree/Plasma/6.7/libnotificationmanager)):
- `GetCapabilities` returns: `body`, `body-hyperlinks`, `body-markup`, `body-images`, `icon-static`, `actions`, `persistence`, `inline-reply`, `sound`, `x-kde-urls`, `x-kde-origin-name`, `x-kde-display-appname` and `inhibitions`. The spec version is "1.2" ([server_p.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/libnotificationmanager/server_p.cpp) L280–305).
- It reads the hints `desktop-entry`, `urgency`, `resident`, `transient`, `category` and several `x-kde-*` hints ([notification.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/libnotificationmanager/notification.cpp) L391–438).
- "Critical notifications must not time out": critical urgency sets the timeout to 0 (L556–567).
- When an action is invoked on Wayland, Plasma first requests an xdg-activation token, then emits `ActivationToken`, then `ActionInvoked` ([server.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/libnotificationmanager/server.cpp) L73–99).

**GNOME Shell** (`main`, 51.0) ([notificationDaemon.js](https://github.com/GNOME/gnome-shell/blob/main/js/ui/notificationDaemon.js)):
- Capabilities: `actions`, `body`, `body-markup`, `icon-static`, `persistence` and `sound`, with spec version "1.2" (L280–301). It honours `urgency` and `resident` (L247–258).
- `ActionInvoked`, `NotificationClosed` and `ActivationToken` are sent only to the unique bus name of the process that called `Notify` (L304–322).
- When that bus name disappears, GNOME destroys the app's notification source (L346–354). An action on a notification whose process has exited therefore reaches no one **[inferred from source]**.

### 2.2 What Tauri's notification plugin provides

- On desktop, `show()` builds a `notify-rust` notification. The doc comment says: "Only the title, body, icon and sound of the notification are used on desktop; the scheduling, grouping and action related options are ignored" ([src/desktop.rs](https://docs.rs/crate/tauri-plugin-notification/2.5.0/source/src/desktop.rs) L28–31). The sound value becomes the `sound-name` hint (L216–218).
- The notification is sent from a background task and its handle is discarded (L240–242), so no action or close event can come back.
- On desktop, the permission check always returns `Granted`.
- The documentation says: "The Actions API is only available on mobile platforms" ([notification.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/notification.mdx) L152–156).
- The desktop code in 3.0.0-alpha.1 still uses `notify-rust` ([CHANGELOG.md](https://docs.rs/crate/tauri-plugin-notification/3.0.0-alpha.1/source/CHANGELOG.md)).

### 2.3 Rust options for actions

- **`notify-rust` 4.18.1.** The default feature `z` uses zbus.
  - `.action(identifier, label)` adds a button ([src/notification.rs](https://docs.rs/crate/notify-rust/4.18.1/source/src/notification.rs) L443–456).
  - Supported hints: `ActionIcons`, `Category`, `DesktopEntry`, `ImageData`, `ImagePath`, `Resident`, `SoundFile`, `SoundName`, `SuppressSound`, `Transient`, `Urgency`, `X`/`Y` and `Custom` ([src/hints.rs](https://docs.rs/crate/notify-rust/4.18.1/source/src/hints.rs) L40–91).
  - `NotificationHandle::wait_for_action` waits for `ActionInvoked` or `NotificationClosed` for that one ID. It passes `"default"` for a body click and `"__closed"` when the notification is closed ([src/xdg/mod.rs](https://docs.rs/crate/notify-rust/4.18.1/source/src/xdg/mod.rs) L99–127; [src/xdg/zbus_rs.rs](https://docs.rs/crate/notify-rust/4.18.1/source/src/xdg/zbus_rs.rs) L114–180).
  - Nothing in the crate handles the `ActivationToken` signal.
- **`zbus` directly.** The same three signals can be subscribed to once for all open occurrences, rather than one wait per notification.
- **`ashpd`.** Covers the Notification portal ([§2.4](#24-the-notification-portal-orgfreedesktopportalnotification)).

### 2.4 The Notification portal (`org.freedesktop.portal.Notification`)

From [org.freedesktop.portal.Notification.xml @1.22.0](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/data/org.freedesktop.portal.Notification.xml), which documents version 2:
- **Notifications outlive the app.** "In contrast to most other portal requests, notifications are expected to outlast the running application. If a user clicks on a notification after the application has exited, it will get activated again." Actions whose names start with `app.` are delivered through D-Bus activation (`org.freedesktop.Application.ActivateAction`) with an `activation-token`. Other actions go out through the `ActionInvoked` signal (L26–52).
- **Fields of `AddNotification(id, vardict)`:**
  - `title`, `body`, `markup-body` (v2) and `icon`
  - `sound` (v2): a file descriptor for ogg/opus, ogg/vorbis or wav, or the strings `default` or `silent`
  - `priority`: `low`, `normal`, `high` or `urgent`
  - `default-action` and `buttons` (each with `label`, `action`, `target` and, from v2, `purpose`)
  - `display-hint` (v2): `transient`, `tray`, `persistent`, `hide-on-lockscreen`, `hide-content-on-lockscreen` or `show-as-new`
  - `category` (v2), including `alarm.ringing` and `weather.warning.extreme` (L54–330)
- **`persistent` is limited:** "Apps are only allowed to display persistent notifications as long as they have a window" (L254–259).
- **Custom alert sounds:** the v2 button purpose `system.custom-alert` lets the server call an app action "to play audio from a special source".
- **Plasma 6.7's backend** runs inside plasmashell as `org.freedesktop.impl.portal.desktop.plasmanotify` and reports **version 1** ([portal_p.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/libnotificationmanager/portal_p.cpp) L60–75, L214–217). When an action is invoked, it passes `activation-token` on Wayland or `desktop-startup-id` on X11 (L120–143). The properties it maps are priority and icon; no sound handling appears ([notification.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/libnotificationmanager/notification.cpp) L486–530). `xdg-desktop-portal-kde`'s `kde.portal` does not list a Notification backend ([kde.portal](https://github.com/KDE/xdg-desktop-portal-kde/blob/Plasma/6.7/data/kde.portal)).

### 2.5 Sounds and the sound theme specification

- **The specifications** (Sound Theme and Sound Naming) were blocked. `notify-rust` describes `sound-name` as "a themeable named sound from the freedesktop.org sound naming specification … An example would be `message-new-instant`" ([src/hints.rs](https://docs.rs/crate/notify-rust/4.18.1/source/src/hints.rs) L66–68).
- **Plasma** reads `sound-file`, `sound-name` and `suppress-sound`. It plays the sound with one `ca_context_play_full` call through libcanberra, and sets the XDG sound theme from `kdeglobals [Sounds] Theme`, which defaults to `ocean` ([notifications.cpp](https://github.com/KDE/plasma-workspace/blob/Plasma/6.7/libnotificationmanager/notifications.cpp) L1044–1100).
- **GNOME** passes `sound-file` and `sound-name` to `MessageTray.Sound` ([notificationDaemon.js](https://github.com/GNOME/gnome-shell/blob/main/js/ui/notificationDaemon.js) L206–214).
- **Playing sounds from the app.** `freedesktop-sound` 0.1.0 implements sound-theme lookup only: `lookup(name).with_theme(..).find()` returns a path, and `list_themes()` lists themes ([README.md](https://docs.rs/crate/freedesktop-sound/0.1.0/source/README.md)). It has fewer than 1,000 downloads. A crates.io search for "canberra" found no libcanberra binding. Audio playback crates were not researched.
- **Looping and escalation.** Neither the notification hints above nor the portal fields define a looping or escalating sound. A loud, repeating alert would need either app-side audio or the portal's `system.custom-alert` purpose **[inferred from source]**.

## 3. Opening the window from the tray, as a single instance

- **Opening from the tray.** With Tauri's default Linux tray backend, a click on the icon produces no event ([§1.2](#12-tray-icon-statusnotifieritem)), so a menu item is the way to open the window. `tao` implements `set_focus` on Linux as GTK `present_with_time(GDK_CURRENT_TIME)`, and visibility as `show_all()` and `hide()` ([src/platform_impl/linux/event_loop.rs](https://docs.rs/crate/tao/0.37.1/source/src/platform_impl/linux/event_loop.rs) L306–315).
- **Single-instance plugin 2.5.0 on Linux.** Using zbus, it requests the session-bus name `<identifier>.SingleInstance`, or `dbus_id` plus `.SingleInstance` if overridden, with name replacement off. It serves `org.SingleInstance.DBus.ExecuteCallback(argv, cwd)` at the matching object path. A second instance that finds the name taken calls that method and exits ([src/platform_impl/linux.rs](https://docs.rs/crate/tauri-plugin-single-instance/2.5.0/source/src/platform_impl/linux.rs) L22–100). Only `argv` and `cwd` are forwarded; no activation token is.
- **Registration order.** The plugin "must be the first one to be registered" ([single-instance.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/single-instance.mdx) L73–76).
- **The name changed.** Version 2.4.0 changed the name from `org.<bundle_id_underscores>.SingleInstance` to `<bundle-id>.SingleInstance`, calling it a breaking change "to follow DBus specifications" ([CHANGELOG.md](https://docs.rs/crate/tauri-plugin-single-instance/2.5.0/source/CHANGELOG.md) L48–52). The documentation page still gives the old name and old Flatpak permissions ([single-instance.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/plugin/single-instance.mdx) L126–199).
- **Flatpak.** By default Flatpak lets an app own "its own namespace named by `$FLATPAK_ID`, subnames of it" ([sandbox-permissions.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/sandbox-permissions.rst) L126–131). If the Tauri identifier equals the Flatpak ID, the new name is such a subname and may need no extra permission **[inferred from source; not tested]**.
- **GTK application ID.** The Tauri config key `app.enableGTKAppId` (default `false`) sets the GTK application ID to the identifier. Tauri's config documentation explains the trade-off: this "lets the desktop environment associate the app's windows with its `.desktop` entry of the same name, which is what makes Wayland compositors and GNOME show the correct icon". The default is `false` "because registering an application ID also makes GTK register the application on the session bus under that ID, which prevents running more than one instance" ([src/config.rs](https://docs.rs/crate/tauri-utils/2.10.0/source/src/config.rs) L3381–3397; used in [tao event_loop.rs](https://docs.rs/crate/tao/0.37.1/source/src/platform_impl/linux/event_loop.rs) L222–229).
- **The generated desktop file** is named `{productName}.desktop` and sets `StartupWMClass` to the executable name. A custom template can replace it ([src/bundle/linux/freedesktop/mod.rs](https://docs.rs/crate/tauri-bundler/2.10.0/source/src/bundle/linux/freedesktop/mod.rs) L106–121; [main.desktop](https://docs.rs/crate/tauri-bundler/2.10.0/source/src/bundle/linux/freedesktop/main.desktop)). Portals, Flatpak and the notification `desktop-entry` hint all identify the app by a desktop-file basename, which is usually a reverse-DNS ID (see the Registry and Background references in [§1.1](#11-xdg-autostart)).

## 4. Location, Wi-Fi, Bluetooth and USB

### 4.1 Location

- **Tauri's plugin.** `tauri-plugin-geolocation` 2.4.0 declares support `none` for Linux, Windows and macOS, and `full` for Android and iOS ([Cargo.toml](https://docs.rs/crate/tauri-plugin-geolocation/2.4.0/source/Cargo.toml) L40–58).
- **The Location portal** (version 1) ([org.freedesktop.portal.Location.xml](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/data/org.freedesktop.portal.Location.xml)):
  - `CreateSession` takes `distance-threshold` (metres), `time-threshold` (seconds) and `accuracy`, from `NONE` (0) to `EXACT` (5).
  - `Start` begins the session.
  - `LocationUpdated` delivers `Latitude`, `Longitude`, `Altitude`, `Accuracy`, `Speed`, `Heading` and `Timestamp`.
- **How the portal gets a fix.** The frontend is built only when `libgeoclue-2.0 >= 2.5.2` is found ([meson.build](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/meson.build) L158–162). It asks GeoClue on the system bus for a client, with the desktop ID `xdg-desktop-portal` ([src/location.c](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/src/location.c) L240–300). It keeps a per-app accuracy permission in the permission store and asks the user through the desktop's Access dialog (L368–424, L530–610). The KDE portal lists an Access backend ([kde.portal](https://github.com/KDE/xdg-desktop-portal-kde/blob/Plasma/6.7/data/kde.portal)).
- **GeoClue directly.** An app can call `org.freedesktop.GeoClue2.Manager.GetClient` on the system bus itself (the same call as `location.c` above). GeoClue's own documentation and configuration could not be read. A third-party crate states that "the user must have a running GeoClue agent or the GeoClue configuration must allow the absence of agent with an empty agent whitelist" ([automatic-timezoned README](https://docs.rs/crate/automatic-timezoned/2.0.159/source/README.md) L23–24; secondary source). Mozilla Location Service, GeoClue's former default for Wi-Fi-based location, retired in 2024, and distributions are switching GeoClue to beaconDB **[unverified: search excerpts, e.g. https://github.com/NixOS/nixpkgs/issues/321121, https://github.com/void-linux/void-packages/issues/55095]**.
- **Rust.** `robius-location` 0.3.1 uses the Location portal first. It falls back to GeoClue directly only when the bus, the portal or the Location interface is missing at startup, "never used after a portal denial, and never for Flatpak/Snap apps". It also supports Android, iOS, macOS and Windows ([README.md](https://docs.rs/crate/robius-location/0.3.1/source/README.md) L6–19). `ashpd` has a `location` module. `geoclue-zbus` 0.2.2 was last released in 2022.
- **In the webview.** `wry` maps WebKitGTK's `GeolocationPermissionRequest` to `PermissionKind::Geolocation` in its permission handler ([src/webkitgtk/mod.rs](https://docs.rs/crate/wry/0.57.0/source/src/webkitgtk/mod.rs) L585–660). Which provider WebKitGTK uses behind this was not verified.

### 4.2 Wi-Fi networks

- **No portal gives the SSID.** The NetworkMonitor portal (version 3) has a `changed` signal and methods for availability, metering, connectivity level (1 = local only, up to 4 = full) and `CanReach(host, port)` ([org.freedesktop.portal.NetworkMonitor.xml](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/data/org.freedesktop.portal.NetworkMonitor.xml)).
- **NetworkManager** (system bus):
  - `org.freedesktop.NetworkManager.Device.Wireless` has `ActiveAccessPoint`, `AccessPoints`, `GetAllAccessPoints`, `RequestScan` (completion shows up as a `LastScan` change via `PropertiesChanged`) and the signals `AccessPointAdded` and `AccessPointRemoved` ([Device.Wireless.xml](https://github.com/NetworkManager/NetworkManager/blob/main/introspection/org.freedesktop.NetworkManager.Device.Wireless.xml)).
  - `AccessPoint` has `Ssid` (bytes), `HwAddress` (BSSID), `Strength`, `Frequency` and `LastSeen` ([AccessPoint.xml](https://github.com/NetworkManager/NetworkManager/blob/main/introspection/org.freedesktop.NetworkManager.AccessPoint.xml)).
  - The `networkmanager` crate 0.5.0 exists but was not reviewed. Hand-written zbus proxies are the alternative.
- **Other network stacks** (iwd alone, systemd-networkd, ConnMan) were not researched.

### 4.3 Bluetooth devices

- BlueZ serves `org.bluez.Device1` at `[prefix]/{hci0,…}/dev_{BDADDR}` on the system bus. `boolean Connected [readonly]`: "A PropertiesChanged signal indicate changes to this status" ([org.bluez.Device.rst](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Device.rst) L14–19, L299–304).
- `bluer` 0.17.4 is "the official Rust interface" to BlueZ. It needs the D-Bus library headers (libdbus) to build, and it was tested against BlueZ 5.60 ([README.md](https://docs.rs/crate/bluer/0.17.4/source/README.md) L1–8, L77–98). Plain zbus proxies of `org.bluez` are the libdbus-free alternative.

### 4.4 USB devices

- On the host, `nusb` 0.2.7 is "pure Rust, no dependency on libusb or any other C library". Its `watch_devices()` yields connect and disconnect events ([README.md](https://docs.rs/crate/nusb/0.2.7/source/README.md) L16–18; [src/lib.rs](https://docs.rs/crate/nusb/0.2.7/source/src/lib.rs) L358–400). On Linux it reads udev's netlink multicast messages ([src/platform/linux_usbfs/hotplug.rs](https://docs.rs/crate/nusb/0.2.7/source/src/platform/linux_usbfs/hotplug.rs) L17–75).
- The USB portal (version 1) offers `CreateSession`, `EnumerateDevices`, `AcquireDevices` and `ReleaseDevices`, plus a `DeviceEvents` signal with `add`, `change` and `remove` actions for active sessions ([org.freedesktop.portal.Usb.xml](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/data/org.freedesktop.portal.Usb.xml) L39–250). Plasma's portal lists a USB backend ([kde.portal](https://github.com/KDE/xdg-desktop-portal-kde/blob/Plasma/6.7/data/kde.portal)).

## 5. What changes under Flatpak

- **D-Bus is filtered.** On the session bus an app may own only its own ID, subnames of it, and its MPRIS name. It may talk only to those, to `org.freedesktop.DBus` and to `org.freedesktop.portal.*` ([sandbox-permissions.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/sandbox-permissions.rst) L124–131). `--system-talk-name=NAME` allows talking to a name on the system bus ([flatpak-run.xml](https://github.com/flatpak/flatpak/blob/main/doc/flatpak-run.xml) L736–742). NetworkManager, BlueZ and GeoClue (if used directly) therefore each need an explicit `--system-talk-name` **[inferred from source]**. Direct `org.freedesktop.Notifications` calls need `--talk-name=org.freedesktop.Notifications`, which is outside the default set above **[inferred from source]**.
- **Tray.**
  - "To use StatusNotifier, you must at least have the `--talk-name=org.kde.StatusNotifierWatcher` permission."
  - An implementation that owns `org.kde.StatusNotifierItem-$PID-$ITEM_ID` needs `--own-name=org.kde.*`, which "introduces many new risks". Current libappindicator works without owning that name ([desktop-integration.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/desktop-integration.rst) L76–101).
  - `ksni` owns that name unless `disable_dbus_name(true)` is set ([src/service.rs](https://docs.rs/crate/ksni/0.3.6/source/src/service.rs) L56–70; [src/lib.rs](https://docs.rs/crate/ksni/0.3.6/source/src/lib.rs) L352–379). `tray-icon`'s KSNI backend does not set it ([ksni/mod.rs](https://docs.rs/crate/tray-icon/0.25.1/source/src/platform_impl/ksni/mod.rs) L30–43).
  - Tauri's Flatpak guide adds `--talk-name=org.kde.StatusNotifierWatcher` and `--filesystem=xdg-run/tray-icon:create`. The second can be avoided with `.temp_dir_path(app_cache_dir)`, because the tray icon image is written to disk ([flatpak.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/distribute/flatpak.mdx) L265–266, L314–322).
  - The guide claims "the Gnome 46 runtime includes all dependencies of the standard Tauri app". Flathub's shared-modules repository does carry `libayatana-appindicator` and `libappindicator` build modules ([libayatana-appindicator-gtk3.json](https://github.com/flathub/shared-modules/blob/master/libayatana-appindicator/libayatana-appindicator-gtk3.json)). Whether the GNOME runtime ships the library was not verified.
- **Autostart** must go through the Background portal ([§1.1](#11-xdg-autostart)). `auto-launch` writes under `$HOME/.config`, which a sandboxed app cannot see by default, and would register the in-sandbox path rather than `flatpak run` **[inferred from source]**.
- **Running without a window.** xdg-desktop-portal compares the compositor's list of apps with windows against the running Flatpak instances every minute. For an app found in the background twice, "if the permission is NO, we kill it; if the permission is YES or ASK, we notify the user" ([src/background.c](https://github.com/flatpak/xdg-desktop-portal/blob/1.22.0/src/background.c) L44–70). Plasma lists such apps in its tray ([§1.2](#12-tray-icon-statusnotifieritem)).
- **Notifications.** Use the portal (see [§2.4](#24-the-notification-portal-orgfreedesktopportalnotification) for Plasma's version 1 limit), or the D-Bus server with `--talk-name`. A `sound-file` path inside the sandbox (`/app/...`) is probably not readable by the host notification server **[inferred, not tested]**.
- **Single instance.** See [§3](#3-opening-the-window-from-the-tray-as-a-single-instance).
- **Location.** Use the Location portal. `robius-location` never uses GeoClue directly under Flatpak ([README.md](https://docs.rs/crate/robius-location/0.3.1/source/README.md) L11–12).
- **Bluetooth.** `--allow=bluetooth` allows `AF_BLUETOOTH` sockets ([sandbox-permissions.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/sandbox-permissions.rst) L82). Reading `Connected` from BlueZ over D-Bus instead needs `--system-talk-name=org.bluez` **[inferred from source]**.
- **USB.** `--device=usb` exposes `/dev/bus/usb` (Flatpak 1.15.11 and later). The USB portal (also 1.15.11 and later) exposes only the devices listed with `--usb=` or `--usb-list` and asks the user before handing over a file descriptor. The documentation notes that `--device=usb` "is broader than what the USB portal is supposed to provide" ([sandbox-permissions.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/sandbox-permissions.rst) L262–372). Whether udev netlink hotplug messages reach the sandbox was not verified.
- **Webview.** Tauri's Flatpak guide lists `--env=WEBKIT_DISABLE_COMPOSITING_MODE=1` as an optional fix for "black webviews on Wayland" ([flatpak.mdx](https://github.com/tauri-apps/tauri-docs/blob/v2/src/content/docs/distribute/flatpak.mdx) L267).

## 6. Wayland-specific problems

- **Raising the window needs an activation token.**
  - When GTK 3 presents a window with no startup ID, it requests a new xdg-activation token from the compositor. The request carries the seat's last implicit-grab serial and the currently focused surface, if any. GTK then activates its own surface with that token ([gdkwindow-wayland.c @gtk-3-24](https://github.com/GNOME/gtk/blob/gtk-3-24/gdk/wayland/gdkwindow-wayland.c) L4003–4047).
  - KWin grants an unprivileged client a real token only when there is no active window, when the requesting surface is the active window, or when the serial is at least as recent as the last user interaction. Otherwise it returns `not-granted-666`. On activation, KWin calls `demandAttention()` instead of activating the window when `mayActivate` refuses ([xdgactivationv1.cpp @Plasma/6.7](https://github.com/KDE/kwin/blob/Plasma/6.7/src/xdgactivationv1.cpp) L59–69, L104–122).
  - A tray-resident app with a hidden window has neither focus nor a recent serial, so a `set_focus()` from a tray menu, a notification action or a second instance may only mark the window as wanting attention **[inferred from source; not tested]**.
  - The tokens the desktop does provide go unused. Plasma supplies them through `ProvideXdgActivationToken` for tray items, the `ActivationToken` signal for notifications, and `activation-token` in the portal's platform data. None of `tray-icon`, `ksni`, `tao`, `notify-rust` or the single-instance plugin handles any of them (no matches for "activation" in their sources).
- **Positioning and stacking.** `tao` marks `set_outer_position`, `outer_position`, `set_always_on_top`, `set_always_on_bottom` and `cursor_position` unsupported or ineffective on Wayland, "since Wayland doesn't support a global coordinate system" ([src/window.rs](https://docs.rs/crate/tao/0.37.1/source/src/window.rs) L163, L235, L721, L736, L1102–1114, L1339). A window cannot be placed next to the tray icon, and the KSNI backend gives no icon rectangle anyway.
- **Tray protocol.** SNI works over D-Bus, so it works on Wayland. XEmbed tray icons need X11 ([desktop-integration.rst](https://github.com/flatpak/flatpak-docs/blob/master/docs/desktop-integration.rst) L73–74).
- **Icons and grouping.** Matching windows to their `.desktop` entry on Wayland depends on the GTK app ID ([§3](#3-opening-the-window-from-the-tray-as-a-single-instance), `enableGTKAppId`).
- **Webview rendering.** See the `WEBKIT_DISABLE_COMPOSITING_MODE` note in [§5](#5-what-changes-under-flatpak).

## Gaps and open questions

1. **Tray clicks.** With Tauri's default backend, clicking the tray icon cannot open the window; only a menu item can. The alternatives are:
   - enabling `tray-icon`'s `ksni` feature through Cargo feature unification (undocumented and untested; it also needs a Flatpak workaround for name ownership),
   - a separate SNI item written with `ksni` directly,
   - waiting for Tauri or `tray-icon` to bind libayatana-appindicator 0.6.0's new `activate-event`.

   Which Plasma version first sends `Activate` when `ItemIsMenu` is false was not checked.
2. **Activation tokens on Wayland.** It was not tested whether KWin actually raises a hidden Tauri window that is shown again after the tray, a notification action or a second launch asks for it. Using the tokens would need code to receive them and pass them to GTK before presenting; no Tauri API for this was found.
3. **Actions after the app exits.** Plain `org.freedesktop.Notifications` actions reach only a running process: GNOME sends signals to the sender only and drops the source when it exits. Portal actions survive through D-Bus activation, which needs a `DBusActivatable` desktop file and an `org.freedesktop.Application` implementation. Neither Tauri nor `tao` provides that implementation (not found in their sources). Plasma's portal backend is version 1: no sound, categories or button purposes. Whether the portal routes notifications from host apps correctly on Plasma was not tested.
4. **Loud and repeating alerts.** Notification servers play the hinted sound once. No mechanism for looping or escalation was found in the interfaces read. App-side audio would need an audio crate (not researched); `freedesktop-sound` only finds files.
5. **Autostart quality.** The Tauri plugin's `auto-launch` 0.5.0 ignores `$XDG_CONFIG_HOME`, does not quote `Exec`, and names the file after the app name rather than its ID. Whether a tray created at login can appear before Plasma's StatusNotifierWatcher exists, and how each backend copes, was not tested.
6. **GeoClue.** Its primary documentation and source were unreachable. Still unverified: whether a GeoClue agent is needed on Plasma, the current default Wi-Fi location service (beaconDB after Mozilla Location Service), and whether it is accurate enough to act as a place **trigger**. Accuracy and privacy trade-offs were not researched.
7. **Wi-Fi without NetworkManager.** Systems using iwd, systemd-networkd or ConnMan were not covered. Whether reading NetworkManager properties needs polkit authorization was not checked.
8. **Flatpak system-bus names.** Whether Flathub review accepts `--system-talk-name=org.freedesktop.NetworkManager`, `--system-talk-name=org.bluez` or `--device=usb` for this kind of app was not checked. The need for those names is inferred from Flatpak's filtering rules, not stated in the documents read.
9. **Desktop-file identity.** Tauri names the desktop file `{productName}.desktop` and leaves `enableGTKAppId` off by default. Portals, Flatpak, notification `desktop-entry` and Plasma's background-app list all key on a reverse-DNS desktop ID. How the host app's ID is established (systemd scope versus `Registry.Register`) under Plasma's autostart was not tested.
10. **Documentation drift.** Tauri's single-instance page gives the pre-2.4.0 D-Bus name, and Tauri's Flatpak guide pins runtime 46 or 47. Tauri 3.0 alphas appeared on 2026-09-21 and 2026-09-26, and everything above describes 2.12.
11. **Specifications not read directly.** Desktop Notifications 1.2, Desktop Application Autostart, Desktop Entry, Sound Theme, Sound Naming and StatusNotifierItem were all blocked. Details such as `Hidden` and `X-GNOME-Autostart-enabled` semantics, and what the specification requires of a server when the notifying app exits, should be checked against the specifications before relying on them.
